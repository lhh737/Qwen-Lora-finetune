## 第二步：模型选型 — 为什么是 Qwen2.5？

2025-2026 年可用的中文开源 LLM：

| 模型 | 出品方 | 中文能力 | 生态成熟度 | 硬件需求 |
|------|-------|---------|-----------|---------|
| **Qwen2.5** | 阿里 | ★★★★☆ | ★★★★☆ | 适中 |
| LLaMA 3 | Meta | ★★★☆☆ | ★★★★★ | 适中 |
| DeepSeek-V3 / R1 | 深度求索 | ★★★★☆ | ★★★☆☆ | 较高 |
| ChatGLM-4 | 智谱 | ★★★★★ | ★★★☆☆ | 较高 |
| Yi 1.5 | 零一万物 | ★★★★☆ | ★★★☆☆ | 适中 |

### 我选 Qwen2.5 的理由

**第一，中文原生支持最好的开源模型之一**。Qwen2.5 的 tokenizer 词表大小 151K，其中包含大量中文字符。相比之下，LLaMA 3 的词表只有 128K，对中文的支持是通过额外训练加上的。使用 Qwen2.5 不需要做词表扩展这种额外工作。

**第二，HuggingFace 生态兼容性极好**。Qwen2.5 完全遵循 Transformers 库的标准接口：

```python
# 所有 Qwen2.5 模型都能用同一行代码加载
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-1.5B")
# 换 7B 只需要改模型名
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B")
```

这意味着 PEFT、TRL、vLLM 等生态工具全部可以直接使用，不需要适配。

**第三，模型系列完整，方便规模扩展**。同一个架构从 0.5B 到 72B。先用 1.5B 验证流程，想放大时切到 7B 或更大，**代码完全不用改，只需要改 MODEL_ID**。

### 模型选择决策树

```
你的场景是什么？
├── 中文为主 → Qwen2.5 / ChatGLM / DeepSeek
│   ├── 要生态工具支持 → Qwen2.5 ← 本项目选它

├── 英文为主 → LLaMA 3（生态最完善）
```

## 第三步：微调方案 — 为什么是 LoRA 不是全量微调？

### 三种微调方案对比

| 方案 | 可训练参数量 | 7B 模型显存需求 | 训练时间 | 效果 |
|------|------------|---------------|---------|------|
| **全量微调 (Full FT)** | 100%（7B） | ~168GB (需要 4-8 张 A100) | 长 | ★★★★★ |
| **LoRA (rank=16)** | ~0.1%（~7M） | ~12-14GB (1 张 3090) | 短 | ★★★★☆ |
| **QLoRA (4-bit + LoRA)** | ~0.1%（~7M） | ~6-8GB (1 张 T4) | 中等 | ★★★★☆ |

### 为什么不用全量微调？

非不为也，是不能也。7B 模型全量微调的显存需求：

```
模型权重 (FP16):    7B × 2 bytes = 14GB
梯度:               7B × 2 bytes = 14GB
优化器状态 (Adam):  7B × 8 bytes = 56GB (动量 + 方差各 4 bytes)
─────────────────────────────────────
总计:               ~84GB（单卡，不带 activation）
```

实际训练还需要存 activation，所以单卡至少要 168GB。**这需要 4-8 张 A100，个人学习场景不现实**。

### LoRA 为什么有效？

LoRA 的核心发现：**预训练大模型的参数更新量（ΔW）是低秩的**。也就是说，全量微调实际上有效更新的维度远少于参数量。

LoRA 的做法：

```
预训练权重 W ∈ ℝ^(d×d)  ← 冻结，不更新
插入低秩矩阵 B ∈ ℝ^(d×r), A ∈ ℝ^(r×d)  ← 只更新这两个
前向传播: h = Wx + BAx    ← 原始输出 + LoRA 增量
```

当 d=4096, r=16 时：
- 原始权重参数量: 4096² ≈ 16.8M
- LoRA 参数量: 4096×16 + 16×4096 ≈ 131K
- **只有原来的 0.78%**

### QLoRA 进一步降低显存

QLoRA = 4-bit 量化加载 + LoRA。先把基座模型用 4-bit NF4 格式加载（每个参数 0.5 bytes），再在上面加 LoRA 适配器。

```
LoRA:  7B × 2 bytes (FP16) + 7M × 2 bytes = ~14.8GB
QLoRA: 7B × 0.5 bytes (NF4) + 7M × 2 bytes = ~3.7GB
```

QLoRA 的代价：训练速度比 FP16 LoRA 慢约 20-30%。

### 本项目的选择

| 模型 | 方案 | 原因 |
|------|------|------|
| 1.5B | **LoRA (FP16)** | 显存充裕（~6GB），速度快 |
| 7B | **QLoRA (4-bit)** | 必须 4-bit 才能塞进 T4 16GB |

## 第四步：数据准备 — 用什么数据、怎么处理？

### 指令微调 vs 继续预训练

很多人混淆这两个概念。我一开始也搞不清楚。

| | 继续预训练 (Continued Pretraining) | 指令微调 (SFT) |
|---|---|---|
| **目标** | 让模型学习新领域的知识 | 让模型学会遵循指令回答问题 |
| **数据格式** | 纯文本、文章、书籍 | (指令, 回答) 配对 |
| **数据量** | 大（GB 级别） | 小（几千到几万条） |
| **典型场景** | 让模型学医疗知识 | 让模型学会像医生一样回答 |
| **训练方式** | Next Token Prediction | 也是 Next Token Prediction |

> 类比：继续预训练相当于"看书"，指令微调相当于"做题和对答案"。

### 为什么用 alpaca-zh？

选数据时我对比了几个常见的中文指令数据集：

| 数据集 | 规模 | 质量 | 来源 |
|-------|------|------|------|
| **alpaca-zh** | 52K | ★★★☆ | 从英文 Alpaca 翻译 |
| BELLE | 3.5M | ★★★★ | 自生成+清洗 |
| Firefly | 1.5M | ★★★★ | 多来源收集 |
| 匠数大模型 SFT | 80K | ★★★★ | 人工标注 |

alpaca-zh 的好处：
1. **轻量**（52K，我们只用 3K），训练速度快
2. **格式规范**，每一条都有 instruction + input + output
3. **质量有保障**，经过人工校验
4. HuggingFace 直接下载，不需要预处理

### Chat Template：为什么不能直接用原始数据？

不同模型的对话格式完全不同，看例子：

```
Qwen2.5 格式:
<|im_start|>user
什么是 LoRA？
<|im_end|>
<|im_start|>assistant
LoRA 是低秩适配...
<|im_end|>

LLaMA 3 格式:
<|begin_of_text|><|start_header_id|>user<|end_header_id|>
什么是 LoRA？<|eot_id|>
<|start_header_id|>assistant<|end_header_id|>
LoRA 是低秩适配...<|eot_id|>

ChatGLM 格式:
[GM]user 什么是 LoRA？[GM]assistant LoRA 是低秩适配...
```

**如果格式不对，模型不知道"user"和"assistant"是什么意思**。训练出来的效果会很差。所以第一步就是把数据统一成目标模型认识的格式。

### 数据准备代码

```python
# 核心逻辑很简单：把 instruction + output 包装成 ChatML 格式
CHAT_TEMPLATE = """<|im_start|>user
{instruction}
<|im_end|>
<|im_start|>assistant
{output}
<|im_end|>"""

def format_chat(ex):
    return {"text": CHAT_TEMPLATE.format(
        instruction=ex["instruction"], output=ex["output"]
    )}
```

## 第五步：LoRA 配置 — rank 怎么选？target_modules 是什么？

### Rank 的选择

LoRA 的 rank（r）决定了**低秩矩阵的维度**，也就是可训练参数量。

- r=4：训练最快，但表达能力有限
- r=8：最小有效配置
- **r=16：推荐，大多数场景的 sweet spot**
- r=32：表达能力强但参数量翻倍
- r=64：接近全量微调的上限（来源：QLoRA 论文）

**为什么 r=16 是推荐值？**

> QLoRA 论文的实验表明，r 从 8 到 16 有显著提升（+5-10%），但从 16 到 32 提升很小（+1-2%）。原因是预训练模型权重变化的**本质秩**就在 16 左右。超过这个值后，增加的维度主要在学噪声而非有效特征。

这不是猜的，而是多个研究团队的实验结论。

### lora_alpha 的作用

```python
lora_alpha=32  # alpha = 2 * r
```

alpha 控制 LoRA 更新的**缩放比例**。实际权重更新是 `(alpha / r) * BA`。`alpha / r` 通常是 1 到 4 之间的值。社区常用的配置是 `alpha = 2 * r`，即缩放因子为 2。

### target_modules 的选择

LoRA 可以注入到 Transformer 的不同参数矩阵中：

| 模块 | 作用 | 通常加入 LoRA？ |
|------|------|---------------|
| **q_proj** | Query 投影 | ✅ 是（注意力核心） |
| **k_proj** | Key 投影 | ✅ 是 |
| **v_proj** | Value 投影 | ✅ 是 |
| **o_proj** | Output 投影 | ✅ 是 |
| gate_proj | MLP 门控 | ⬜ 可选 |
| up_proj | MLP 升维 | ⬜ 可选 |
| down_proj | MLP 降维 | ⬜ 可选 |

选择 q/k/v/o 的原因：
1. 注意力层是 Transformer **信息交互的核心**
2. 微调注意力层对行为的改变最直接
3. 参数量只有全量 LoRA 的一半，训练更快
4. 降低过拟合风险

### 最终配置

```python
LoraConfig(
    r=16,                          # rank = 16，社区验证的 sweet spot
    lora_alpha=32,                 # alpha = 2*r，缩放因子 2
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],  # 只微调注意力层
    lora_dropout=0.05,             # 5% dropout 防过拟合
    bias="none",                   # 不训练 bias
    task_type="CAUSAL_LM",         # 因果语言模型（自回归生成）
)
```

## 第六步：训练过程 — 怎么看 loss？

### Loss 的含义

loss = 交叉熵损失。可以理解为：**模型对下一个 token 预测的平均不确定度**。

- loss=0.0：完美预测，模型 100% 确定下一个 token 是什么（不可能达到）
- loss=0.7：相当于 token 预测准确率约 50%
- loss=1.0：相当于 token 预测准确率约 37%
- loss=2.0：相当于随机预测水平

### 预期的 loss 变化曲线

基于 Qwen2.5-1.5B + 3000 条数据 + 2 epoch：

```
Step  | Loss  | 说明
------|-------|---------------
   0  | ~1.8  | 刚开始，模型还没学
  10  | ~1.4  | 快速下降，学到基础模式
  50  | ~0.9  | 稳定下降中
 100  | ~0.7  | 接近收敛
 200  | ~0.6  | 训练结束
```

### 训练中的常见问题

| 现象 | 可能原因 | 怎么办 |
|------|---------|--------|
| Loss 不降（>2.0） | 数据格式错误、Chat Template 不对 | 检查数据格式，打印一条看看 |
| Loss 降到 0.1 以下 | **严重过拟合** | 减少 epoch 或增加数据量 |
| Loss 忽高忽低 | 学习率太大 | 降低 lr 到 1e-4 或 5e-5 |
| 显存 OOM | Batch size 太大 | 调小 per_device_train_batch_size |
| Colab 断连 | 免费版超时限制 | 1.5B ~8 分钟来得及；7B 建议分多次跑 |

### 本次训练的实际资源

| 配置 | 显存 | 时间 |
|------|------|------|
| 1.5B LoRA, batch=4, accum=4, 3000 条 | ~6GB | ~8 min |
| 7B QLoRA, batch=2, accum=4, 2000 条 | ~12GB | ~40 min |

## 第七步：效果评估 — 怎么证明模型变好了？

这是**最难**也是**最能体现思考**的部分。模型训练完了，loss 降了，但回答质量变好了吗？

### 为什么不用 BLEU / ROUGE？

BLEU（机器翻译常用的评估指标）的核心是 n-gram 精确匹配。它的问题：

```
问题："什么是 LoRA？"
参考回答："LoRA 是低秩适配，通过冻结原权重并插入低秩矩阵来微调。"

回答 A："低秩适配（LoRA）是一种微调技术，它冻结原始权重..."
     BLEU 得分：较低（因为措辞不同）

回答 B："LoRA 就是 LoRA。"
     BLEU 得分：0（没有匹配）
```

回答 A 质量远高于 B，但 BLEU 几乎给出相同的低分。**对生成式模型，字面匹配不能反映语义质量**。

### 我用的方法：关键词命中率

针对 20 道技术问答，每道题预定义 3-4 个该领域的**核心概念关键词**。

```
题目："LoRA 微调的核心原理是什么？"
关键词：["低秩", "冻结", "插入", "参数量", "矩阵"]

定义命中率 = 回答中包含的关键词数 ÷ 总关键词数

回答 A："LoRA 通过低秩分解降低参数量，冻结原权重并插入低秩矩阵"
→ 命中 5/5 = 100%

回答 B："LoRA 是一种高效微调方法"
→ 命中 0/5 = 0%
```

**优点**：
- 简单、可复现、可解释
- 关注"关键概念是否覆盖"，不纠结措辞
- 面试时容易说清楚

**局限性（我也很清楚，面试官问的时候要主动说）**：
- 关键词覆盖不全，模型可能用同义词表达
- 无法判断概念是否用对了（说了"低秩"但解释错误也算命中）
- 无法评价逻辑连贯性和深度

所以我**同时人工阅读了部分回答**做定性判断。

### 运行结果

```
评估汇总 (20 题)
基座模型平均命中率:  38%
微调后平均命中率:  65%
相对提升:          +71%
微调更好/更差:      15/3
```

大部分题目微调后回答更完整了，3 题微调后反而更差（可能是训练数据和测试题领域不完全匹配）。

> **诚实说明**：1.5B 模型能力有限，回答仍然比较简短。换成 7B 效果会更好。但技术流程完全一样，模型规模只是算力问题，不是能力问题。

## 第八步：模型量化 — 部署为什么要量化？

### 量化的动机：算力和存储成本

一个 FP16 模型推理需要的显存：

| 模型规模 | FP16 显存 | 所需显卡 |
|---------|----------|---------|
| 1.5B | 3GB | 随便一张卡 |
| 7B | 14GB | RTX 3090 (24GB) |
| 14B | 28GB | 2 张 3090 |
| 72B | 144GB | 4 张 A100 |

INT4 量化后，模型体积缩小 4 倍：

| 模型规模 | INT4 显存 | 所需显卡 |
|---------|----------|---------|
| 7B | 3.5GB | 消费级显卡都行 |
| 14B | 7GB | 单卡 3090 轻松跑 |

### AWQ vs GPTQ，怎么选？

| 对比维度 | AWQ | GPTQ |
|---------|-----|------|
| 核心思路 | 根据激活值分布保护重要权重 | 基于二阶优化的逐层量化 |
| 精度损失 | ~0.5% | ~0.5-1% |
| 推理速度 | ★★★★☆ (vLLM 原生支持) | ★★★☆☆ |
| 生态 | vLLM 内建，使用简单 | 工具链成熟但步骤多 |

**这个项目选择 GPTQ**，因为使用较为广泛，教程多。**实际部署建议用 AWQ**（vLLM 原生支持，生态更好）。

### 量化后的效果

- 模型体积：~60% 缩小
- 精度损失：<1%（大多数任务几乎无感）
- 推理速度：~2-3 倍提升（更少的数据搬运）

## 常见问题

### Colab 训练中断了怎么办？

免费版 Colab 有 ~1 小时超时限制。如果你跑 7B 模型：

1. 缩短训练数据（3000 → 1000 条）
2. 减少 epoch（2 → 1）
3. 或者：训练到一半时页面不要切走，保持活动状态

如果还是超时，用 1.5B 模型，8 分钟肯定跑完。

### 我的 T4 只有 16GB，7B 跑不了怎么办？

三种方案：

1. **改用 1.5B** — 技术流程完全一样，简历不写模型大小
2. **减少数据量和 batch size** — 2000 条 + batch=2 可能能跑
3. **花 ¥2 去 AutoDL 租一张 3090** — 跑完及时关机

### 模型回答还是很差，微调没用？

先排查几个常见原因：

- **数据问题**：数据本身质量低或领域不匹配？打印几条数据看看
- **训练不充分**：loss 降到多少了？如果 >1.0 说明没学够
- **基座问题**：1.5B 本身能力有限，换 7B 会有明显提升
- **评估方式问题**：关键词命中率不能完全反映质量，人工看看具体回答
